# Processing-mode pipeline check

> **Historical audit:** This is a snapshot of an earlier investigation. Findings and tool behavior may have changed. See the [specification guide](../README.md) and [open questions](../open-questions.md) for current information.

This is an exploratory test of current working trees, not a specification
release or proof of complete ISA-PHM or ISA graph conformance.

## Evidence

- Wizard `conversion-payload.contract.test.js` passes its existing 12 tests,
  including separate raw-only and processed-only payload assertions. This is a
  JavaScript unit/contract test, not a browser-to-Backend export test.
- `experiments/test_processed_only_placeholder.py` now also exercises raw
  only, raw plus processed, and processed only from a synthetic Backend payload
  through converter serialization, selected layout and PHM protocol checks,
  then Wrapper `raw`, `processed` and `auto` loading. Temporary CSVs contain
  distinct values to make accidental selection observable. All three modes
  passed this test; the inputs were not generated by the Wizard in this run.
- The existing processed-only round-trip test also passed: the current
  placeholder is a pathless `Raw Data File` with `availability: not included`;
  the Wrapper loads processed data and rejects explicit raw loading. The
  isatools default configuration test in that experiment does not establish
  complete ISA graph conformance; see Decision 0017.

## Confirmed processing-description loss

**Update:** the current Backend working tree now exports the selected
processing protocol's description, and the Wrapper exposes protocol
descriptions via `assay.list_protocols()`. Cross-repository tests cover a
description, an empty value and `Unknown`. Previously exported files are not
repaired, and this does not establish a required unknown-state workflow.

The Wizard's test-setup UI lets the researcher edit a processing protocol's
name and description. In an in-memory Backend converter experiment, a selected
processing protocol was given the distinctive description `PROCESSING_SENTINEL:
high-pass filter at 100 Hz`, and the setup sensor was given a distinct sensor
description. The generated `Processing Protocol` contained the sensor
description instead, and did not contain the processing description. The
converter's `app/converter/entrypoint.py` constructs that description from
`sensor.get("description", "")`. Processing parameters are mapped separately;
this experiment does not establish loss of all processing metadata.

This is a provenance defect: users may believe their explanation of processing
was exported when it was not. The existing selected protocol presence and
lineage checks do not detect the defect, because they do not compare its
description to the user's input or validate scientific adequacy.

## Remaining work

1. Verify the description path in a complete browser-to-Backend export and
   decide how to express an unknown method without fabricating one.
2. Add a true cross-repository test that starts with a Wizard-generated payload
   for each mode and checks conversion, validator results, and Wrapper behavior.
   The tests above are complementary but not that continuous pipeline.
3. Complete independent ISA core schema and applicable ISA content/graph checks
   on all modes; evaluate alternatives to the processed-only placeholder before
   declaring it normative. Verify processing that changes rate or unit.
4. Test real processed datasets and multiple files/runs; the synthetic test
   uses one sensor and one run. A real dataset may have different provenance
   and semantics.
